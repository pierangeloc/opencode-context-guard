I built this as a plugin while waiting for it, and the experience of using it
suggests a couple of things worth considering if it does become built in:
<https://github.com/pierangeloc/opencode-context-guard>

**The number that matters is `input + cache.read`, not output.** Every turn
re-sends the whole window, so a session that reaches 200k tokens and then runs
another 200 turns bills those 200k tokens 200 more times. In one month of my
own usage that re-reading was around 90% of the spend. Watching only output, or
only the session's cumulative cost, does not show it coming.

**Window share is the wrong unit.** 137k tokens is 14% of a 1M-token window and
still re-read in full on every turn — about $0.21 a turn on a frontier model.
A percentage-of-window indicator reads as reassuring exactly when the warning
matters most. Absolute token counts, with the share shown as secondary
information, turned out to be much harder to misread.

**Where the warning goes matters more than I expected.** A toast is gone in
seconds and a desktop notification is easy to miss. The thing that actually
changed my behaviour was a persistent line in the sidebar, under the context
figure that is already there, which stays until the context is cleared.

Two notes on the plugin API I ran into, which may be worth a line in the docs:

1. For a plugin loaded from a local directory, the root `index.ts` / `tui.tsx`
   are what resolve; the `exports` map in `package.json` applies when it is
   installed as a package. With only `exports`, the server half loaded and the
   terminal half was silently absent.
2. Relative imports in a plugin need their extension, including `.tsx`.
   `export { default } from "./src/tui"` makes the loader look for
   `./src/tui.ts` and give up. It does log
   `plugin operation failed ... stage=read` in the client log, which is the
   only place it shows up — the terminal itself looks fine, just without the
   plugin.

Happy to fold any of this into core if that is useful.
